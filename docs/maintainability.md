# Maintainability analysis

The current implementation provides the planned Tsguard code, structure and change levels with measurable maintainability protection to the existing CLI and schema-1 result contract. No extra workflow or agent handoff is required. Existing Level 1 gates still fail fast and retain their thresholds.

```sh
npm install -D @oxguard/tsguard
npx tsguard check --output agent
npx tsguard maintainability --output json
npx tsguard change --baseline HEAD --output json
```

## Implemented Tsguard levels

| Level | Implemented behavior | Execution |
|---|---|---|
| 1 — Code | Ultracite/Biome lint, formatting and cognitive cap; FTA; TypeScript; native typed lint; coverage; secrets, dependency CVEs and SAST; unused code and duplication | Existing blocking check gates; Knip in audit; jscpd advisory in check/audit |
| 2 — Structure | Resolved function/method and runtime module graphs; caller/callee counts, criticality, fan-in/out, SCC depth/cycles, coupling; forwarding chains, fragmented forwarding modules and handler policies | Advisory maintainability in check; focused smells/structure/criticality commands |
| 3 — Change | Explicit inert Git baseline; native file FTA/cyclomatic/Halstead distribution, per-function cognitive bounds, clone/token changes, structural/coupling/delegation deltas; conservative file/symbol matching | Advisory change in check when a baseline is available; focused change command, which exits 1 when the comparison is incomplete |

The Python runtime module graph (cycles, `TYPE_CHECKING`/deferred-import controls, SCC dependency depth and per-module fan-in/fan-out coupling), function graph, delegation/async-delegation reviews and failure-policy reviews are implemented as advisory parity milestones through grimp 3.18 and pyan3 2.9.0; Python P7a adds explicit inert Git comparison for structural aggregates and Radon file metrics; function-complexity matching and duplication remain later milestones. These levels describe supported deterministic analyses, not exhaustive type safety, runtime architecture inference or proof of behavioral equivalence. Single-use functions, recursion and file counts alone are not quality violations. No prescribed architecture/layer framework is required.

## Quality policy

Without a lint config, the npm distribution extends pinned Ultracite 8.0.1 (with Biome 2.5.15) and applies quality baseline version 1. The baseline explicitly pins cognitive complexity at the existing limit of 20, empty blocks, useless catches, unsafe non-null assertions, unreachable code, constant conditions and other established Biome rules. `lint.baseline_version` records its use. This does not claim those rules were previously missing from Ultracite.

Project Biome configuration, disabled rules and flat ESLint/Oxlint configurations remain authoritative. Legacy ESLint names are recognized so fallback Biome does not silently replace them; support still depends on upstream Ultracite/ESLint, and unsupported execution is an error or partial normalization. The flat ESLint path is tested but its native diagnostics are not yet normalized. Project configs are never overwritten.

PyGuard follows the same principle for exception handling in zero-config Python projects. Without a project Ruff configuration (`[tool.ruff]`/`[tool.ruff.*]` in `pyproject.toml`, `ruff.toml` or `.ruff.toml` at the root), it adds blocking Ruff S110 (try-except-pass) and B012 (jump in finally) to every Ruff lint invocation it owns and records `ruff.baseline_version`. S110 keeps Ruff's default scope: `pass`-only bare/`Exception`/`BaseException` handlers are flagged, while `except ValueError: pass` is not. Projects that configure Ruff are unaffected: no extra flags, no recording and no override of their `ignore` policy. Unreadable or malformed configuration keeps the existing Ruff invocation, and Ruff's own `# noqa` and test-file behavior is retained. See [Complexity metrics](metrics.md).

Biome with pinned Ultracite presets owns syntax lint and formatting. A separate `typed-lint` gate runs only five upstream compiler-aware rules through pinned Oxlint 1.88.0 / oxlint-tsgolint 7.0.2004, with all syntax categories disabled. No ESLint engine, JS lint plugin or second formatter is added. `types` and structural analysis retain the selected project TypeScript compiler.

`check` runs lint → FTA → types → typed-lint → coverage → security, then advisory maintainability/duplication/change. Native unsafe assignments, unsafe narrowing assertions, floating promises and misused promises are blocking. Unnecessary conditions are advisory because type assumptions may differ from runtime inputs. Native defaults, including explicit `void` promise opt-out, remain upstream policy; an opt-out does not prove safe error handling.

The backend uses TypeScript 7 semantics, independently of the project compiler version. It requires strictNullChecks and resolved, compiler-valid declarations. Supported-config fixtures use the current 5.9 project/compiler path without claiming semantic equivalence to TypeScript 7. Removed options such as baseUrl, native type/configuration diagnostics, missing declarations and scopes over the portable 24000-character file-argument budget leave typed lint partial and nonblocking; missing installed engines or malformed reports are execution failures. Select a smaller scope or migrate unsupported native options deliberately. Semantic scope follows the configured directories/exclusions and existing exclude-tests default; selected files and that policy are recorded in the native artifact. No root config is overwritten and no executable Oxlint config is loaded. Native reports record tool versions, selected rules, project compiler and native diagnostics in `node_modules/.cache/oxguard/typed-lint/native.json`; stale reports are removed before each invocation.

Existing explicit project ESLint/Oxlint policy is still respected through the compatibility path. Such projects must supply their own engine. The zero-config package invokes Oxlint only for the separate semantic gate, not a competing syntax/format policy. Node support requires 22.18+ on the 22.x line, 24.x, or 26+ (Ultracite 8).

## Advisory rules

| Rule | Evidence | False-positive boundary |
|---|---|---|
| LONG_DELEGATION_CHAIN | At least three resolved single-return sync/async layers preserve positional arguments and return type | A single boundary is not flagged; methods, generic/default/rest/optional parameters and transformations are excluded; async timing/stack boundaries remain review judgments |
| FRAGMENTED_DELEGATION | The forwarding chain crosses at least three modules whose analyzed functions only forward | File counts alone never produce a finding; constants and other module-level responsibilities still require human review |
| LONG_DELEGATION_CHAIN (PyGuard) | At least three module-level, undecorated Python forwarding layers preserve positional arguments and identical textual return annotations | Methods, nested/decorated functions, generic/default/rest/keyword-only/positional-only parameters and transformations are excluded; async layers must use `return await` to another `async def` |
| FRAGMENTED_DELEGATION (PyGuard) | A PyGuard forwarding chain crosses at least three files whose analyzed module-level functions only forward | Classes and other module statements do not disqualify a file; a module with a real function stops fragmentation, and forwarding cycles produce no delegation finding |
| REPEATED_ERROR_HANDLER | At least three identical catch token sequences of at least 12 tokens | Identifiers/literals are preserved, so different failure policies are not equated; comments are ignored |
| SILENT_EXCEPTION_FALLBACK | Catch body consists only of a literal, bare-value, empty-array or no-value return | Intentional best-effort policies remain valid; review the evidence, do not automatically change propagation or add payload logging |
| SILENT_EXCEPTION_EXIT | Catch body only continues or breaks | Recorded/propagated recovery is excluded; intentional best-effort policy remains valid |
| REPEATED_ERROR_HANDLER (PyGuard) | Three or more Python handlers share at least 12 body tokens | Fingerprints use body-only Python tokens and preserve identifiers/literals; comments are ignored |
| SILENT_EXCEPTION_FALLBACK (PyGuard) | A broad handler contains only a return of no value, a constant, another bare name, or an empty list/tuple/dict | Bare `except`, `Exception`, `BaseException` and tuples containing them qualify; `pass` is excluded because Ruff S110 covers it; `()` and `{}` qualify, `set()` does not |
| SILENT_EXCEPTION_EXIT (PyGuard) | A broad handler contains only `continue` or `break` | Typed handlers are excluded; all handlers still count for repeated-body detection |
| SILENT_PROMISE_REJECTION | Native promise catch callback only returns a literal/empty array | Recorded or transformed recovery is excluded; advisory, not a forced rethrow |
| DISCARDED_SETTLED_REJECTION | Native allSettled through const aliases into a flatMap block; explicit status guards expose an empty-array rejected path without a reason reference | Bounded path analysis, not arbitrary data flow or a reachability proof; reason references suppress warnings but do not prove recovery |
| CIRCULAR_DEPENDENCY | A runtime import strongly connected component, including a self-loop | Type-only imports do not create runtime cycles |
| HIGH_MODULE_COUPLING | At least three in-scope importers and eight in-scope runtime dependencies | Advisory review cue; counts do not establish poor cohesion |
| POSSIBLE_COMPLEXITY_DISPLACEMENT | Per-file branch concentration or native FTA maximum decreases, total branches do not, edges increase and depth, wrappers or cycles increases | Smaller files alone do not trigger it; branch reduction is a negative control |
| NEW_DEPENDENCY_CYCLES | Candidate has more cyclic runtime components than baseline | Advisory, not an architecture prescription |
| INCREASED_COUPLING | More modules meet the joint fan-in/fan-out review threshold | Counts do not establish poor cohesion |
| FUNCTION_COMPLEXITY_INCREASE | Matched native cognitive lower bound exceeds the prior upper bound | Required domain complexity remains valid |
| NEW_DUPLICATION | Native clone token fingerprint has additional matches | File moves alone are not new duplication |

`check` includes established jscpd duplication analysis after the blocking gates. Its existing minimum match policy is retained; repeated validation and general boilerplate use upstream detection instead of another custom clone engine. Duplicate findings remain advisory. Short repeated catch policies have their own AST-backed evidence below typical general clone thresholds.

## Structure and scope

One compiler pass produces function/call facts, catch fingerprints and module edges for the new smell/structure/change path. Existing criticality reuses the compiler-input helper. Typed lint has its own native semantic program plus a compatibility preflight; it is not part of the reusable graph pass.

Module IDs are root-relative paths. Function IDs contain file, source position and symbol; edge IDs identify their endpoint pair. Findings retain the existing stable schema-1 IDs. IDs are deterministic for the same inputs, not rename-tracking identities across arbitrary refactors.

The graph artifact is `node_modules/.cache/oxguard/maintainability-graph.json`. JSON includes fan-in/out, SCC condensation depth, cycle components, branch observations, forwarding depth, external/type-only imports and unresolved references. Module and function call depth are the longest path between SCCs, not an invented depth within a cycle. Distinct function callers/callees and recursive components are measured in regular analysis without another compiler pass. Functions also include forwarding_mode, max_branch_nesting and branch_locations. Nested callbacks reset branch nesting at their own boundary. These branch observations are not FTA or cognitive scores. Structured FTA cap failures collect complexity-context for only the first failing file, retaining the original failure and not running later check gates.

Source scopes and directory exclusions apply. Dependency directories, `.git`, declaration files and conventional generated files are excluded; conventional test files/directories follow the existing exclude-tests option. Dynamic nonliteral and missing local imports make graph assessment partial. External and out-of-scope dependencies are boundary counts, not inferred graph edges. CommonJS require, dynamic literal imports, re-exports and compiler path aliases are supported. Runtime dispatch, bundler-only resolution and import assertions beyond static compiler resolution are not proven.

PyGuard provides the corresponding runtime module-graph subset with grimp 3.18 and NetworkX 3.7 through `pyguard structure`. In-scope runtime import edges form SCCs; `module.count`, `module.edges`, `module.cycles`, `module.type_imports`, `module.deferred_imports` and per-module `module.dependency_depth`, `module.fan_in` and `module.fan_out` use the same units and level as Tsguard. Imports under `if TYPE_CHECKING:` are type-only and excluded from runtime edges, while function/method-local imports are deferred and excluded from edges/cycles; both remain counted. External imports are not edges. Import roots come from the project layout, independently of graph scope: files under `<project>/src` use `src` as their root (including the default `.` scope and narrowed `--dirs` paths inside `src`), and every other file uses the project root. Identities are full dotted paths below those fixed roots including namespace directories, and import names never rename files. Resolution inventories all `.py` files under those roots; scope, exclusion and test filters only select graph nodes, so an existing out-of-scope target is a boundary rather than a missing module or parent fallback. `from X import name` validates the name against the full inventory (submodule, subpackage, or an AST-defined/exported `__init__` name) before the boundary applies. Export validation is a deliberate over-approximation: a name counts as exported when any statement in the package `__init__` AST can bind it, at any nesting level, including ordinary `if`/`elif`/`else` branches, `try`, `while`, `match`, `with`, function bodies (including `global` declarations), `Store` names, `def`/`class` names, import aliases and except/match targets. Only bodies of `if TYPE_CHECKING:` blocks and annotation-only `AnnAssign` statements are excluded. It also accepts Python-provided module attributes such as `__path__`, `__name__`, `__spec__` and `__file__`, and any name when the package `__init__` defines module-level `__getattr__`, performs a runtime `from ... import *`, or assigns through `globals()`/`setattr()`. Because exports are over-approximated, only a clearly missing name makes the result incomplete. Namespace-package `from . import x`/`from pkg import x` validates its child module/package. Unresolved or invalid relative imports never reach grimp, and a grimp resolver panic is reported as incomplete `not_evaluated` evidence rather than an execution failure. A runtime SCC, including a self-loop, yields one advisory `pyguard.structure.CIRCULAR_DEPENDENCY` warning that never changes the exit code or blocking outcome; like Tsguard, a cycle can turn an otherwise passing overall/gate status into `advisory`. A module with at least 3 distinct in-scope runtime importers and at least 8 distinct in-scope runtime dependencies also yields one advisory `pyguard.structure.HIGH_MODULE_COUPLING` warning with the module as its location; the fixed thresholds are review cues, not an architecture rule. Fan-in/fan-out count distinct in-scope runtime modules only: `TYPE_CHECKING`-only, deferred and external imports do not count, out-of-scope/excluded/test modules are boundaries, and a self-import remains one runtime edge and one cycle but is not counted as its own importer or dependency. A missing module inside a project package root, a duplicate module identity or an unparsable file leaves the assessment incomplete with `pyguard.structure.not_evaluated`; source parsing uses Python's own byte-level encoding detection (UTF-8 BOM and PEP 263 declarations), matching grimp's `tokenize.open` line numbers. missing/broken grimp or NetworkX is an execution error. The command also runs in informational `audit` and as the `structure.module_graph` `diagnose` analysis, but is not part of `pyguard check`. Python layer rules are not claimed; the P7a comparison subset is described below.
The same command builds the corresponding advisory function call graph with pyan3 2.9.0 and NetworkX 3.7. In-scope defined functions, including methods and nested functions, get `function.fan_in` (distinct defined callers), `function.fan_out` (distinct defined callees) and `function.call_depth` (longest path between call SCCs), using the same `structure` level and `callers`/`callees`/`edges` units as Tsguard. `function.recursive_components` counts call SCCs with more than one function or a self-loop, and `calls.unresolved` is a deterministic own-scope `ast.Call` site count rather than a pyan3 placeholder/wildcard edge count. For each defined in-scope function it visits calls in that function's own scope only: nested `FunctionDef`/`AsyncFunctionDef`/`ClassDef` bodies are separate callers and are not descended into, lambda and comprehension bodies stay with the enclosing function, and a nested definition's decorators/defaults (and annotations) belong to the enclosing scope. A call site is resolved when its target is a `Name` or `Attribute` whose terminal name (`Name.id`/`Attribute.attr`) equals the short name of a callee in that caller's resolved in-scope function edges (including a self-call), a `Name` that is a Python builtin, or a `Name`/`Attribute` chain rooted at a name bound by an import statement in that module. Every other call site is unresolved, including subscript or call-result targets such as `items[0]()` and `f()()`, local aliases such as `saved = callback; saved()`, parameters and closure variables, and attribute receivers whose name is not a resolved in-scope callee or imported root such as `obj.run()`. Each call site counts once and receivers are never separate call sites; there is no alias or dataflow tracking, so this is a syntactic approximation. Repeated resolved calls still form one graph edge; a self-call is one call edge and one recursive component but is not its own caller or callee, so `function.fan_in` differs from the unchanged `pyguard criticality` `criticality.in_degree` only for self-recursive functions (criticality counts the self-call once). Calls from module-level code, external targets and out-of-scope functions are not edges. The function graph itself emits no findings and never changes the exit code or blocking outcome; separate delegation reviews are described below, and neither is part of `pyguard check`. `tokenize.detect_encoding` decides whether pyan3's forced UTF-8 read would misread a source: every source whose declared or BOM encoding is not plain UTF-8, including a non-UTF-8 source whose bytes also happen to decode as UTF-8, is mirrored as UTF-8 for pyan3 with original locations and pyan3's original inferred import root preserved, even when an ancestor `__init__.py` marker is outside the requested scope; an unparsable file leaves the assessment incomplete with `pyguard.structure.not_evaluated`, while missing/broken pyan3 or NetworkX is an execution error.

PyGuard also reports advisory delegation smells from the same pyan3-resolved in-scope function edges. Only a module-level, undecorated `def`/`async def` with plain positional-or-keyword parameters and a body of exactly one `return <Call>` (an optional leading docstring is allowed) can forward. The call must be a bare `Name` whose unique resolved in-scope target is another function, and its arguments must be the parameters as bare `Name` nodes in the same order, with no keywords or starred arguments. Return annotations are compared as `ast.unparse` text: both absent or textually identical, never one-sided. A plain `def` returning a call is `sync`; an `async def` forwards only as `return await b(...)` to another `async def` (`async-return-await`), so an un-awaited async return or an await of a non-async target is not forwarding. Every function gets `delegation.depth` in `layers` (a forwarding cycle has no finite suffix and is reported as 0), and every forwarding function gets `delegation.forwarding` (value 1, `calls`) with the additive measurement fields `forwarding_mode` and the module-qualified `forward_target`. `pyguard.structure.LONG_DELEGATION_CHAIN` is emitted at depth 3 or more with the chain as related locations, and `pyguard.structure.FRAGMENTED_DELEGATION` when the chain crosses at least three files whose analyzed module-level functions all forward; classes and other module statements do not disqualify a file, while a module with a real function only stops fragmentation. Both findings are advisory warnings in category `quality`, never change the exit code or blocking outcome (they can turn an otherwise passing status into `advisory`), and remain outside `pyguard check`. Methods, nested and decorated functions, default/rest/keyword-only/positional-only parameters, transformed or reordered arguments, annotation mismatches, test files and forwarding cycles are controlled boundaries. The same analysis runs through `audit` and `diagnose`.

PyGuard also reports advisory failure-policy findings from `pyguard structure` (including through `audit` and `diagnose`, but not `check`). `SILENT_EXCEPTION_FALLBACK` covers exactly one `return` of no value, a constant, a name other than the caught `as` name, or an empty `[]`, `()` or `{}`; `set()` and other calls are excluded. `SILENT_EXCEPTION_EXIT` covers exactly one `continue` or `break`. Python applies fallback/exit only to bare, `Exception`, `BaseException`, or tuples containing a broad handler, and excludes `pass` because Ruff S110 covers it. Typed handlers remain excluded from those two findings. `REPEATED_ERROR_HANDLER` considers every handler, including typed and `except*`, and groups body-only `tokenize` sequences after dropping comments and layout tokens while preserving identifiers and literals; three or more handlers with at least 12 tokens produce a finding at the first handler with the others in `related` and `observed` equal to the group size. All three rules are advisory warnings in category `quality`, use fixed thresholds and no configuration, and never change exit code or blocking outcome. They use the same in-scope non-test files and encoding handling as the Python structure graph; an unparsable file produces incomplete `pyguard.structure.not_evaluated` evidence. The `maintainability.failure_policies` capability is implemented with real-binary and stand-in cases for broad silent fallback, loop exits, caught-name and typed/pass controls, empty-literal boundaries, repeated-handler thresholds and literal sensitivity, `except*`/method/module scope, test exclusion and parse failure.

## Safe change comparison

Set `--baseline <Git ref>` or root `oxguard.toml` `baseline`. The ref resolves to an immutable commit SHA. Exact Git blobs are read with ls-tree/cat-file into a bounded private source snapshot; export-ignore/export-subst cannot hide or rewrite the input. Symlinks, submodules and dependency trees are not exported. Nested project prefixes are supported. Project source, package scripts, baseline dependencies and hooks are never run to produce measurements.

Comparison reuses candidate structural facts and analyzes the baseline with the trusted current compiler. The snapshot limits are 20,000 copied files, 8 MiB per file, 128 MiB total source and a 4 MiB Git tree listing. Missing compiler/config dependencies, missing scopes and unresolved local imports remain errors or not-evaluated comparisons, not passes.

No baseline means `change` remains not_run and assessment is incomplete; the focused command exits 1, while an optional comparison never changes check’s blocking outcome. Report the missing optional comparison without inventing a quality failure. Baseline/candidate module, edge, cycle, dependency-depth, fan-in/out, coupling, function call depth, wrapper and branch-distribution measurements are emitted separately. No aggregate maintainability score or behavioral-equivalence claim is produced.

Native comparison metrics reuse the installed FTA, Biome and jscpd engines. Both revisions are projected into private, bounded directories containing only graph-selected source. No baseline or candidate analyzer configuration, application code, dependency code or package script is loaded there. Identical pinned analysis policy is recorded in `node_modules/.cache/oxguard/maintainability-change.json`; the result links this artifact. Existing project policy and thresholds for regular lint/FTA/duplicates gates remain unchanged.

FTA comparison includes short files with `exclude-under: 0`, per-file scores/cyclomatic/Halstead volume, maximum/p50/p90 score distributions and matched-file deltas. Native jscpd compares exact clones with its established 50-token/5-line minimum; token fingerprints retain identifiers/literals, omit trivia and count multiplicity independently of file location. NEW_DUPLICATION reports additional native clone matches, including independent validation that still needs human review.

Biome's cognitive rule has a minimum diagnostic threshold of 1. An isolated measurement pass records exact scores above 1 and honest [0,1] bounds below it. FUNCTION_COMPLEXITY_INCREASE requires a matched candidate lower bound above the baseline upper bound. Inline cognitive suppressions leave unknown upper bounds and partial assessment; they cannot be turned into zeroes. Source changes during measurement, malformed/native tool failures and missing metrics are explicit execution errors. No lint threshold is changed by these measurement passes.

File identity first uses the existing path, then only unique exact source hashes for moves. Functions first use a unique file/qualified-symbol key, then a unique exact token fingerprint. Line movement does not erase matching evidence. Ambiguous copies and arbitrary semantic renames stay unmatched; the artifact records the matching method and both profiles. A move is not a simplification claim.

Full runtime call depth, arbitrary semantic rename inference, custom branch-expression scores and domain responsibility inference remain outside static analysis. The supported displacement checks combine lower per-file branches or native FTA maximum with unreduced branch work and increased structural cost. These facts do not prove every possible displacement or behavioral equivalence.

## Evaluation and parity

`evals/maintainability.cjs` and `evals/review-gaps.cjs` run adversarial cases through the packed installed launcher in the existing npm/pnpm platform matrix. It tests the baseline, Biome syntax policy plus semantic-only native rules, preserved project policy, valid DI/boundaries/validation, exact repeated handlers, exception propagation/recording/fallback, runtime/type-only cycles, generated exclusions, deterministic IDs, bounded agent output, artificial splits, real branch reduction, missing refs, nested projects and inert baseline scripts/export attributes. It never runs in an ordinary guard invocation.

The existing 30 TypeScript and 37 Python Level 1 cases remain. Additional not-run gates are explicitly allowed in the historical fail-fast oracle; all original gate states/findings remain exact, and installed tests separately require the new candidate gate list. New Python capabilities are deferred independently unless explicitly implemented, and deferred capabilities are not scored as passing; `quality.zero_config_exception_handling` is implemented through Ruff S110/B012 with blocking zero-config cases, a logging-versus-pass contrast, project-config/`noqa` controls, ellipsis and typed-exception boundaries and Ruff's preserved test-file coverage; `quality.cognitive_complexity` is implemented through complexipy 8.3.0 with advisory execution, flat, nested, nested-function folding, test-exclusion and threshold-boundary cases. `structure.runtime_graph` and `structure.false_positive_controls` are implemented through grimp 3.18 with runtime-cycle, self-loop, nested-package, namespace-package, namespace-relative-import cycle, acyclic-chain/depth, scope/test-exclusion, duplicate-identity, `TYPE_CHECKING`-only, external-import, external-name-collision, deferred-import, excluded-target, default-scope src-layout cycle, narrowed-scope boundary and missing-child, package-export, invalid-relative-import and unresolved-local cases; it also covers Python-provided module dunders closing a real package cycle, exports bound by import aliases, loop/with/except targets, walrus assignments and `global` declarations, module `__getattr__` and star re-exports, and dynamic `globals()`/`setattr()` exports. `structure.function_graph` is implemented through `pyguard structure` with the four criticality-semantics cases plus Tsguard-parity, resolved method and nested-function, mutual-recursion SCC depth, test-file exclusion, unresolved-dynamic-call and unparsable-`not_evaluated` controls; it also covers builtin/import/in-scope resolved calls, local aliases and receiver reads each counting one unresolved call site, and a closure parameter attributed only to the nested caller. Function fan-in/out exclude self-calls while `pyguard criticality` keeps its unchanged self-call in-degree. `maintainability.delegation` is implemented with a resolved `a->b->c->real` chain that reports both delegation findings at advisory exit 0, direct/equivalent and DI/validation/boundary controls, argument-transformation and return-annotation-mismatch controls, default/rest/keyword-only/positional-only and decorated-wrapper boundaries, a depth 2-versus-3 threshold, a forwarding cycle with depth 0 and no finding, test-file exclusion, and a module with a real function that keeps `LONG_DELEGATION_CHAIN` but not `FRAGMENTED_DELEGATION`. `maintainability.async_delegation` is implemented with an async `return await` chain that records `async-return-await`, an un-awaited async chain that never forwards, and an await of a non-async target boundary. `maintainability-capabilities.json` lists appropriate Python providers and explicit gaps; `maintainability-parity.cjs` cannot turn those gaps into release readiness.

Tsguard release readiness is assessed for the selected Ultracite/Biome maintainability scope with installed evals, retained Level 1 checks and the existing platform matrix. New Python maintainability parity is a later milestone and does not block that scope. `tsguard_scope_ready` and `pyguard_maintainability_ready` are separate report fields; a passing scope report alone does not replace platform checks or authorize publication. Broader independent repository evaluation remains a useful follow-up, not a new mandatory release ceremony.

## Agent review responsibilities

The bundled Tsguard skill reads the target project's applicable AGENTS.md and referenced policies. It reviews helper purpose, shared policy, recovery visibility, event ownership and whole-workflow complexity. Those judgments cite code/project policy and remain separate from native findings. The skill does not impose a new project architecture document, require every catch to rethrow, or infer duplicate runtime logs from event names alone. Read-only review can run focused smells/maintainability after fail-fast; it cannot turn unexecuted gates into passes.

## PyGuard change subset

`pyguard change --baseline HEAD --output json` compares the same candidate scope and exclusion policy against inert Git blobs through the existing structure pipeline and candidate-installed Radon. It reports module/function graph aggregates, wrappers, Radon CC/MI/Halstead file metrics and path-identical CC/MI deltas. `POSSIBLE_COMPLEXITY_DISPLACEMENT` requires per-file reduction plus unreduced branches, added runtime edges and increased depth/wrappers/cycles; new cycles and coupling hotspots have separate advisory findings. Complete comparisons exit 0 even with findings; absent/unavailable baselines, partial inputs, version disagreement and unavailable metrics leave focused change incomplete and exit 1. `check --baseline` adds advisory evidence while preserving its existing blocking outcome and exit code; check without the flag is unchanged.

P7a retains the structure analyzer's `.py` source semantics (`.pyi` blobs are retained but not measured), candidate scope/test/exclusion policy on both sides, bounded regular-blob materialization and automatic temporary-tree cleanup. It never executes baseline source or configuration. It adds no function/fingerprint matching, duplication comparison or change artifact. The `change.complexity_displacement` and `change.false_positive_controls` eval capabilities are implemented; function-complexity and broader truthful-completeness parity remain planned, so this subset does not claim complete Python maintainability parity. See [metric definitions and limits](metrics.md#pyguard-git-baseline-comparison-p7a).
